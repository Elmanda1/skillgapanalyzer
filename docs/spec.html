1. Introduction

1.1 Purpose

This document specifies the design of the Skill Gap Analyzer: a Curriculum Intelligence system that quantitatively compares supply (curriculum Learning Outcomes / RPS from vocational programs) against demand (skill requirements extracted from thousands of real job postings) and classifies the resulting gaps using a standard mismatch taxonomy — not a binary “gap / no gap” verdict.

The SDD is the reference for all implementation work. It fixes module boundaries, data contracts, algorithms, and API surface so that parallel workstreams (Python data engine, Laravel backend, React frontend) can proceed independently.

1.2 Scope

In scope: web scraping, NLP/ETL, main database, analysis engine (matching + classification), Laravel backend API, React/Inertia dashboard, curriculum input.

Out of scope for v1: automatic PDF parsing of RPS documents (manual structured entry instead), multi-institution federation, real-time streaming of job data (weekly batch is enough).

Market scope (locked 2026-08-12): v1 is constrained to the IT/technology job market as a pilot slice. KMIPN.pdf names TI only as an example (“misalnya … jurusan Teknologi Informasi”) and otherwise speaks generally of “pasar kerja” incl. manufacturing; this SDD deliberately narrows the shipped slice. The pipeline (scraper → ETL → DB → engine → API → dashboard) is market-agnostic by design — the taxonomy seed list is the only market-specific component, so adding manufacturing/accounting/healthcare later is a second taxonomy slice, not an architecture change. IT-only is the defensible demo scope; the multi-market story stays in the proposal.

2. System Overview

2.1 Problem

Vocational graduates face a structural skills mismatch with industry. Prior approaches fail: tracer studies are retroactive and subjective (~9.8% variance explained), manual link-and-match lacks data, job portals give no analytic feedback. There is no objective, measurable, updatable instrument for detecting skill gaps at per-skill granularity.

2.2 Goals

  1. Extract and map Learning Outcomes from vocational curriculum program structures.
  2. Automatically collect and analyze competency demand from thousands of job postings (text/data mining).
  3. Produce an objective, periodically updatable skill gap map, classifying mismatches per the international taxonomy.
  4. Give concrete recommendations: which skills/topics to add or deepen in the curriculum.

2.3 Stakeholders

Stakeholder Role
Dev team (hackathon) Build architecture, backend logic, NLP, UI
Vocational institutions (e.g. Politeknik) Supply data: RPS, syllabi, Learning Outcomes
Industry / career platforms Demand data source: job postings (scraped or via public API)
Students End users of learning recommendations; UAT feedback

2.4 Success criteria

  • Match-rate percentage per study program is reproducible from the same data snapshot.
  • Gap classification matches the 8-type taxonomy, not binary.
  • Weekly demand refresh is idempotent and does not corrupt history.
  • Dashboard renders thousands of skill points without degrading interaction.

4. Module Specifications

4.1 Web Scraper (Data Collection) — complexity ★★★

Purpose: Scheduled, automated crawling of job portals (LinkedIn, JobStreet) for job title + skill-requirement text.

Inputs: portal URLs/pages; scheduled trigger (weekly); per-source scrape config. Outputs: raw job postings (title + requirements text) with source + timestamp metadata.

Design decisions - Per-source adapter with configurable selectors (portals have heterogeneous DOM). - Partial-failure resilience: one dead source must not kill the batch; per-source error isolation and retry with backoff. - Anti-bot/rate-limit/ToS: polite crawl settings (rate limiting, robots.txt respect, UA rotation only where lawful); prefer public APIs where available. - Freshness: weekly scheduled re-run; each run tagged with scrape_batch_id. - Selector churn: keep selectors in config, not code; alert on zero-yield per source. - Volume (D4): 500–1,000 postings per run from a single portal source; no queue/worker infrastructure — a single Python script completes one run in minutes. - Trend backfill (D6): first run pulls postings dated over the past ~3 months (per portal-provided date), preserving real posted_at; subsequent runs are incremental (new/updated only).

Open questions: LinkedIn/JobStreet ToS — legal scrape surface vs. API; which single source is primary (open — see Q6); volume target per run (proposal says “ribuan lowongan”).

Locked (D2): demo day runs seed-first — a real scrape + real ETL run is executed days before and loaded into the DB as a snapshot. A dashboard-triggered “Refresh data” job re-runs the batch live on jury demand; this proves the pipeline without making it load-bearing. ponytail: in v1 the refresh is a demo-triggered job, not a scheduled cron — add the cron when the system runs unattended post-hackathon.

4.2 Data Processing & ETL (NLP extraction/normalization) — complexity ★★★★

Purpose: Turn unstructured job text and curriculum docs into clean, deduplicated, categorized skill entities.

Inputs: raw job texts; raw curriculum docs (RPS / Learning Outcomes); standard skill taxonomy + synonym dictionary. Outputs: normalized skill entities; deduplicated skill lists; structured records ready for DB load; historical demand trend series.

Design decisions - Normalization pipeline per document: cleaning → tokenization → skill extraction → synonym resolution → taxonomy mapping → dedup. - Extraction: TF-IDF keyword scoring as baseline; IndoBERT NER for Indonesian text (no off-shelf Indonesian skill extractor — Spacy/NLTK pipelines must be customized). - Standard taxonomy (e.g. Docker ≡ containerization) is the single source of truth; synonyms table drives resolution. - Idempotency: re-running a batch produces identical DB state (upsert keyed by source hash); batch ID on every record. - Weekly scheduled; incremental (only new/updated postings) with full-history preserved.

Open questions: taxonomy size/curation process for v1; accuracy target for extraction (precision vs recall for gap claims).

4.3 Main Database — complexity ★★★

Purpose: Unified, queryable, auditable store modeling curriculum ↔︎ skill ↔︎ job-demand relations.

Inputs: ETL output (skills, trends); manual curriculum/profile input; analysis results. Outputs: unified structured store; versioned snapshots for trend/reporting queries.

Design decisions - Relational model (see §5). Laravel Eloquent as ORM. - Versioned snapshots of demand trends (time-series of skill frequency per source/month) for trend queries. - Auditability: immutable ingestion log; every row traceable to source batch or manual entry user. - Integrity constraints (FKs, uniqueness on taxonomy canonical names) enforced at DB level, not app level.

4.4 Analysis Engine — complexity ★★★★★

Purpose: The “brain”. Match supply vs demand at per-skill granularity, classify each gap into the mismatch taxonomy, score match rate.

Inputs: normalized curriculum skill profiles (supply); normalized demand trends (demand); static taxonomy reference. Outputs: skill gap map per program/skill; match-rate %; mismatch-type classification per gap; prioritized gap list.

Design decisions - Matching: per-skill comparison of supply (present in curriculum / student profile) vs demand (frequency + trend in postings). Degree weights per study program adjust how strongly each skill counts (e.g. core-course skill > elective skill). - Scoring: match rate = weighted matched skills / weighted demanded skills (see §7). - Classification: rule-based mapping onto the 8-type taxonomy (see §6), using demand trend + supply presence/level. - 5 competence dimensions (incl. Task management, Contingency management) covered via dimension tags on taxonomy entries; non-hard-skill dimensions scored by manual/curriculum evidence (they are hard to measure from text — explicitly flagged in UI as estimate, not measurement). - Deterministic: same snapshot → same result (no stochastic components), so results are auditable and reproducible.

Open questions: exact weight scheme per program; threshold definitions per taxonomy type; how to source non-hard-skill evidence in v1.

4.5 Backend API (Laravel) — complexity ★★

Purpose: Bridge between analysis logic and UI; serve analytic data; auth for two roles (lecturers / students).

Inputs: HTTP requests (dashboard queries, auth); Analysis Engine results. Outputs: JSON: gap maps, trend series, reports, recommendations; session/auth tokens.

Design decisions - API contract versioned and stable while engine internals evolve (engine output → DTO layer → JSON contract). - Roles: lecturer (program-level reports, curriculum input) and student (personal recommendations). Role-based middleware. - Complex relational queries for dashboard aggregation run server-side; pagination for thousands of skill points.

4.6 Dashboard Output (React + Inertia.js + Tailwind) — complexity ★★

Purpose: Three output types in one UI: (1) trend visualization of industry skill demand over time, (2) prioritized learning recommendations for students, (3) detailed program-level gap reports.

Inputs: backend API responses. Outputs: match-rate dashboard (proposal Gambar 1); interactive Skill Gap Map rendering mismatch taxonomy (Gambar 2); trend charts; learning recommendation list; gap report downloads.

Design decisions - React via Inertia.js (server-driven pages, no separate SPA API layer needed). - Interactive skill gap map must stay responsive with thousands of skill points → canvas/SVG aggregation, virtualized lists, server-side filtering.

4.7 Curriculum Input — complexity ★

Purpose: Structured manual entry of RPS / Learning Outcomes and student skill profiles by program staff.

Inputs: RPS / Learning Outcome documents; student skill profiles (manual entry). Outputs: structured curriculum/skill profile records → Main Database (supply side).

Design decisions - Forms + validation only. No parsing intelligence in v1. - ponytail: PDF/doc parsing can be layered on later, moving this module’s complexity up — add when curriculum staff adoption requires it.

  │

  │

  │

  │
scrape_batches (id, source, started_at, finished_at, status, item_count)
  │
job_postings (id, scrape_batch_id, source, source_url UNIQUE, title, raw_text_hash, posted_at)
  │

  │
demand_trends (id, taxonomy_id, period, frequency, source)                   -- versioned snapshot
  │

             demand_level, match_rate, mismatch_type[8-taxonomy], score)
  │
recommendations (id, user_id | study_program_id, taxonomy_id, priority, rationale)

5.2 Key constraints

  • job_postings.source_url unique → natural idempotency key for ETL upserts.
  • skill_taxonomy.canonical_name unique → single normalization target.
  • FKs enforced at DB level; gap_results written once per (program, skill, period) — upsert on re-analysis.
  • demand_trends append-only; period + source + taxonomy_id composite unique.

6. Mismatch Taxonomy (Classification)

Adapted from Vázquez-Villegas & Borrego (2026) 8-type framework. Each gap is classified by a decision rule combining supply presence, demand level, and demand trend.

# Type Signal (supply / demand) Classification rule (v1)
1 Overeducation skill taught, not demanded supply present, demand ≈ 0
2 Underskilling skill demanded, taught insufficiently demand > 0, supply present but below threshold
3 Skill shortages skill highly demanded, absent from curriculum demand high + rising, supply absent
4 Skill gaps demand present, supply partial demand > 0, supply present at low level (distinct from underskilling by severity/threshold)
5–8 (remaining types per framework) per framework definitions map when reference taxonomy is fully imported

5 competence dimensions (Isnandar et al., 2024) tag each taxonomy entry: hard/technical skills + non-hard dimensions incl. Task management and Contingency management. Non-hard dimensions are scored from curriculum/manual evidence and labeled “estimate” in the UI.

Open question: exact thresholds (demand frequency, supply level) per type — set during Analysis Engine spike, validated against a labeled sample.

7. Matching & Scoring

Per program P, per period T:

demand_set(P,T)   = skills demanded by industry (frequency ≥ threshold, weighted by degree relevance)
supply_set(P,T)   = skills present in curriculum of P (weighted by credits/course level)

match_rate(P,T)   = Σ weight(s) for s ∈ (supply ∩ demand)  /  Σ weight(s) for s ∈ demand
gap(s, P, T)      = demand_level(s) − supply_level(s), per taxonomy type (§6)
priority(s, P, T) = gap severity × demand trend slope × dimension weight
  • Weights: per study program (degree weights), per skill (course credits / core vs elective).
  • Outputs: match-rate %, per-skill gap map, prioritized recommendation list.
  • Determinism requirement: same snapshot in, same numbers out.

9. Non-Functional Requirements

  • Performance: dashboard interactions stay responsive with thousands of skill points (server-side aggregation, canvas/SVG rendering, pagination/virtualization).
  • Security: role-based access (lecturer vs student); student data scoped to own profile; DB-level integrity; secrets (portal credentials, API keys) in env, never in code.
  • Reliability: scraper partial-failure isolation; ETL idempotent (re-run safe); scheduled jobs recover from missed runs.
  • Auditability: every analytical claim traceable to scrape batch / manual entry / taxonomy version; snapshots versioned.
  • Maintainability: API contract decoupled from engine internals; selectors/config externalized.

12.2 Decision Resolutions (Research-Backed)

The following are resolutions and recommendations for the skipped and open questions from the grill session, based on industry best practices and research:

Phase 2: Core Engineering & Tech Stack

  • Q6 (Portal): JobStreet is recommended for Indonesian tech jobs due to lower ToS/anti-bot risks for batch scraping (500–1,000) compared to LinkedIn.
  • Q9 (NLP Extraction): Hybrid approach: TF-IDF for baseline explicit keywords, and IndoBERT (e.g., IndoBERTSkill) for Named Entity Recognition to accurately extract implicit skills and score higher in the AI competition.
  • Q10 (Taxonomy): Use a manageable subset of ESCO or O*NET (150–200 core IT skills) for v1 to ensure standard nomenclature.
  • Q11 (Accuracy bar): Aim for >85% precision on a manually labeled test set of 100 job postings.
  • Q17 (DB Engine): PostgreSQL is recommended over MySQL due to its superior native JSON support and full-text search capabilities for NLP data.
  • Q18 (Snapshot retention): Keep all history, but aggregate older data (roll up weekly into monthly averages after 6 months) for production.
  • Q19 (API Versioning): Implement /api/v1 as standard practice to show professional architecture.

Phase 3: Taxonomy & Pedagogy Validations

  • Q12 (5 Competence Dimensions): Tag and show non-hard skills (like Transfer Skills) as "Estimated" from curriculum inputs rather than strictly scoring them from job texts, as they are notoriously noisy to extract.
  • Q13 (Mismatch Taxonomy): Use a standard framework focused on: 1. Overeducation, 2. Underskilling, 3. Skill Shortages, 4. Skill Gaps, 5. Overskilling, 6. Undereducation, 7. Field-of-study Mismatch, 8. Skill Obsolescence. Focus the algorithm on #2, #3, #4, and #8 for the demo.
  • Q14 (Degree weights): Store as a JSON config (degree_weight_config) in the study_programs table, editable via the lecturer dashboard.
  • Q15 (Validation against Azalia 2021): The system validates the finding that traditional skills match well, but specific modern IT/technical skills show undersupply.
  • Q16 (Supply levels): Calculate a baseline using the Bloom's Taxonomy Verb mapped to a level, multiplied by course credits. Allow manual lecturer override.

Phase 4: UI/UX & Demo Data

  • Q20 (Auth): Seeded accounts only for v1 demo (1 Lecturer, 2 Students) to save time, with strict user_id scoping for student data privacy.
  • Q21 (Chart library): Use Recharts or Chart.js for trends, and a Scatter Plot (X: Demand, Y: Supply) for the Skill Gap Map to visualize critical shortages (bottom-right quadrant).
  • Q22 (Report export): PDF is highly recommended (via dompdf or spatie/laravel-pdf) to "wow" stakeholders and the jury.
  • Q23 (Data entry scope): One (1) study program (e.g., D4 Teknik Informatika) with 5-10 core courses manually seeded by the dev team for perfect demo data quality.
  • Q24 (Student profiles): Program-level baseline gap + 1 manually self-reported student profile to demonstrate personalized recommendations.

13. Glossary

  • RPS — Rencana Pembelajaran Semester (semester lesson plan)
  • LO — Learning Outcome / Capaian Pembelajaran
  • Supply — skills taught by the curriculum (or held by a student profile)
  • Demand — skills required by industry, extracted from job postings
  • Match rate — weighted share of demanded skills covered by supply
  • Mismatch taxonomy — 8-type classification framework (Vázquez-Villegas & Borrego, 2026)
  • IndoBERT — Indonesian-language BERT model for NER
  • ETL — Extract, Transform, Load
